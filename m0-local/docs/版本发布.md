# 版本发布说明

本工程从 **0.6.0** 开始保存完整 Git 源码版本。0.1.0～0.5.0 只留下阶段文档和验证证据，没有完整源码快照，无法准确还原当时工程。

## 标签的含义

| 标签 | 内容 | 能否取得该版本源码 |
| --- | --- | --- |
| `history/v0.1.0`～`history/v0.5.0` | 按版本分别提交的历史文档与证据记录 | 不能；属于 `documentation-only` |
| `v0.6.0` | 当前 0.6.0 源码提交 | 可以；本地组件和依赖须按说明准备 |
| 后续 `v版本号` | 对应版本经过验证的准确源码提交 | 可以；按该版本说明准备依赖 |

历史记录标签不等于旧版软件发布。不得将当前代码修改版号后包装为旧版，不得用同一当前源码提交冒充多个旧版本。GitHub 为历史标签自动生成的源码压缩包，也不代表当年完整源码；如建立历史 Release，应在标题和正文明确写出“仅历史文档，无源码快照”。

版本清单保存在 [versions/index.json](../versions/index.json)，各阶段单独记录保存在 `versions/v版本号.md`，面向阅读的变化总表为 [CHANGELOG.md](../CHANGELOG.md)。当前 GitHub 仓库为私有仓库 `jinny-wj/m0-local`，脚本以已确认的 `origin` 为发布目标。

每版可上传的验证摘要保存在 `versions/evidence/v版本号.json`，包含来源文件相对路径、字节数、SHA-256，以及白名单检查结果、计数与限制。原始 `diagnostics/` 被 Git 忽略，不上传仓库。摘要不复制原始日志、个人绝对路径、凭据、项目或会话数据；来源哈希用于核对当时本地证据，不代表这些原始文件已公开。

## 发布命令

```sh
npm run release
```

默认只校验版本、记录、Git 目标与待提交内容，不提交、不建标签、不推送，也不创建 Release。应先准备好本版代码与版本文档。

```sh
npm run release -- --publish
```

正式发布会执行测试、提交当前改动、建立版本标签、推送分支与标签并创建 GitHub Release；如果有本版运行组件附件，也会上传到 Release。既有版本标签保持不变，不能在源码变化后复用；应先递增版号。

如需为对应平台准备可选的恢复运行组件附件，先运行：

```sh
npm run release:runtime
```

归档输出到被 Git 忽略的 `.release-assets/`，随后由发布命令上传本版归档与校验文件。运行组件附件与源码分开保存；只在确实需要发布附件时生成，并检查适用平台和组件来源说明。

## 每次升级的流程

1. 完成该版本的代码与必要验证，保留有明确范围的检查结果。区分真实界面/服务联调、测试模型和模拟节点，不扩大验收结论。
2. 同步 `package.json`、`package-lock.json`、服务返回的版本号及该版本实际使用的其他版本标识，检查它们一致。
3. 更新 `CHANGELOG.md`，新增 `versions/v版本号.md`，并在 `versions/index.json` 登记日期、`source-release`、正式标签和证据位置。
4. 检查提交内容：只包含该版本所需的源码、依赖清单、公开资源和可分享文档。个人模型配置、密钥、Figma 登录资料、配对令牌、项目会话、运行数据与缓存不提交。需要本地准备的恢复组件在说明中列出来源与步骤。
5. 将准确源码提交到 Git，再以 `v版本号` 建立带说明的标签。发布后保持原标签不变；修复应产生新提交和新版本。
6. 向已经确认的 GitHub 仓库推送提交与标签，为该版本创建或更新 Release，写明具体变化、验证范围、准备步骤和仍需登录/配置的能力。
7. 核对远端提交、标签与 Release 一致，确认版本列表保留此前所有记录。最终提供仓库和该次版本的链接。

历史 0.1.0～0.5.0 的文档应分别提交、分别标记历史标签；0.6.0 使用完整源码提交和正式标签。后续每一版均按正式源码流程发布，避免再次只有文档而没有对应代码。
