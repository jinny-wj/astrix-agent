# 复刻码灵（M0 Design）实施方案

<!-- anchor:overview -->
## 1. 概述

复刻快手内网设计工具 M0 Design（码灵），最终目标是获得一条**面向视觉设计（人物海报 / 资源位）的批量出图能力**，且产出物为**可编辑图层**而非死像素。

方案分三阶段，按确定性从高到低排列，**每阶段独立可交付**：

| 阶段 | 内容 | 确定性 | 阻塞依赖 |
|------|------|--------|----------|
| P0 | 首页视觉 1:1 还原 | 100% | 无，可立即开始 |
| P1 | Figma 集成载体技术验证（Spike） | 待验证 | 需 Figma token / 权限 |
| P2 | 人物海报批量生成流水线 | 有风险 | 需内部模型通道信息 + 素材 |

**核心判断**：P0 不依赖任何外部信息，先做掉；P1 是架构分叉点，选错载体返工成本极高，必须先验证再动手；P2 有一票否决项（人脸保真）尚未解决。

### 4.2 载体选型结论（Spike 部分作废）

原三条路径的对比仍然成立，但**选型已由证据确定**：

| 证据 | 推出的结论 |
|------|-----------|
| 顶部有「编辑器 / Figma」双模式切换 | 存在自建编辑器，Figma 只是其中一种视图模式 |
| 左侧独立「图层」面板 | 拿到了完整图层树，**iframe embed 不可能做到**，排除路径甲 |
| 画布有选中框 + 顶点手柄 | 自建渲染与交互层，非嵌入第三方画布 |
| 悬浮工具条（分割/移除背景/修改/标注/生成原型/AI热区） | 对选中节点做 AI 操作，需完整节点数据 |
| 右下「画布可编辑」状态 + 缩放比例 | 自建画布的编辑态标识 |
| 「同步我的个人文件」 | 后台批量拉取 Figma 文件，对应首页「同步中」徽章 |

→ **确定为路径丙：REST API 拉取 + 自建画布渲染与编辑。**

### 4.3 R6 核实的关键 API 事实（R7 修正）

已查证 Figma 官方 REST API 文档：

| 事实 | 影响 |
|------|------|
| REST API 能力范围为 Files / Images / Versions / Users / Comments / Projects / Components，**设计内容均为只读**；可写的仅 Comments、Webhooks、Dev resources、Variables | **写回设计内容不可行**，必须自建数据结构 |
| 文件列举路径：`GET /v1/teams/:team_id/projects` → `GET /v1/projects/:project_id/files` | 需先有 team_id / project_id |
| 官方明确：team_id 无法编程获取，须从 team 页面 URL 手动取 | **一次性人工配置即可解决，非硬阻塞** |
| 存在 `projects:read` scope，描述为「List projects and files in projects」 | 遍历文件列表是官方支持能力 |
| `GET /v1/files/:key` 返回完整节点 JSON（位置、文字、填充等） | 图层树可完整获取 |
| Scope 文档明确：`You can only access files that you've created or that have been shared with you` | **本人 token 可访问本人创建的全部文件，含个人草稿** |

### 4.3.1 「同步很慢」反证的实现机制（R7 关键修正）

R6 曾判断「打开即同步个人文件」在公开 API 下不可行。**该结论被用户反馈推翻**：用户指出该功能可用，只是**同步很慢**。

「慢」这一现象本身就是实现方式的证据链：

| 观察 | 推论 |
|------|------|
| 同步耗时明显 | 不是单次请求，而是**多次串行 API 调用** |
| 首页存在持久化的「同步中」徽章 | 后台异步任务 + 轮询进度，而非同步阻塞返回 |
| 若为内部特权接口，本可一次性批量返回 | 慢恰恰说明它走的是**公开 REST API 的常规路径** |

推定实现：
1. OAuth 授权（`projects:read` + `file_content:read` 等 scope），用**用户自己的身份**
2. 遍历用户可见的 team → project → files（多次请求，逐级下钻）
3. 逐个文件拉缩略图与元数据（文件多则请求数线性增长）
4. 受 REST API 速率限制，需退避重试 → **这就是慢的根因**

关键认知修正：**scope 文档写明本人 token 可访问「本人创建的」文件**。此前误读为「个人草稿完全不可达」，实际不可达的是**他人**的私有草稿。用户自己的文件（含 Drafts）在授权后是可枚举的，只要能拿到对应的 project_id。

### 4.3.2 修正后的能力边界

| 能力 | 原判断 | 修正后 |
|------|--------|--------|
| 自动同步个人文件 | ❌ 不可行 | ✅ **可行**，走 OAuth + 遍历，慢是固有代价 |
| 写回 Figma 原文件 | ❌ 不可行 | ❌ 不变（REST 无设计内容写接口） |

因此 P1-b 应从「用户贴链接手动导入」升级为「OAuth 授权 + 后台遍历同步 + 进度轮询」，与原产品行为一致。

### 4.4 P1 实施拆解

按依赖顺序分四步，每步独立可验证：

**P1-a 编辑器界面骨架（无阻塞，可立即做）**

- 右侧 AI 面板：欢迎卡、3 步引导、11 个能力标签、输入框、状态栏
- 悬浮工具条（分割/移除背景/修改/标注/生成原型/AI热区）
- 交付：像素级还原的静态编辑器界面，画布内为占位内容

**P1-a2 Agent 对话流（R8 新增，来源：需求文档回放截图）**

文档中「方式1: skill+M0+模版」的三张过程截图揭示了 Agent 对话的消息结构，需还原以下区块类型：

| 区块 | 内容 | 依据 |
|------|------|------|
| 用户气泡 | 蓝紫渐变、右对齐 | 「这几个重新分别出3个方案」 |
| 上下文引用 | 「参考 N 个上下文」可折叠 + Figma 图标条目，条目含尺寸与输出要求 | 「热门活动-弹窗 840*1120 输出要求≤300kb png/jpg」等 3 条 |

| 上下文采集摘要 | 「collected context 读取 5 · 搜索 1 >」 | 灰色单行摘要 |
| 工具调用卡 | 工具名 + 动作 + `success` + 节点 ID + 备注，内嵌设计预览 | 「读取设计稿 · success · 节点 346:20940 · 含设计预览」 |

| 批量结果 | 多规格产出物列表 | 「批量生成」输出态 |

实现方式：脚本化回放（无后端），发送消息后按上述结构逐区块呈现，用于验证信息架构与视觉。真实 Agent 接入在 P1-b 之后。

**P1-b Figma 文件同步（需 OAuth 或 token）**
- OAuth 授权（scope: `projects:read` + `file_content:read` + `file_metadata:read`）
- 后台异步任务：遍历 team → project → files，逐个拉元数据与缩略图
- 进度轮询 + 首页「同步中」徽章联动；速率限制退避重试
- 备选：单文件链接直接导入（快速通道，无需等待全量同步）
- 交付：授权后自动列出个人文件，与原产品行为一致

**P1-c 画布渲染与交互（依赖 P1-b）**
- 节点树 → 绝对定位 DOM/Canvas 渲染（FRAME/RECT/TEXT/IMAGE 优先）
- 选中框、顶点手柄、缩放、平移
- 交付：能在自建画布上看到并选中真实设计稿元素

**P1-d 编辑与导出（依赖 P1-c）**

- 导出：PNG/JPG，以及可选的 Figma 文件生成
- 交付：闭环的「导入 → 编辑 → 导出」

## 5. P2：人物海报批量生成流水线

### 5.1 能力边界（D03 已定）

> **AI 只处理人像，其余全部由程序承担。**

一张海报中仅「把低质主播照修成可用人像」需要模型；背景、模板套用、标题排版、标签替换、多规格导出全是确定性程序工作。此切法同时压低 credits 消耗与不可控风险。

### 5.2 流水线

```
素材文件夹 + 信息表 + 海报模板
        ↓
① 素材预处理（OpenCV，零消耗）
   人脸检测 / 构图判定 / 抠图 / 基础校正
        ↓
② 人像修复（模型介入，唯一消耗点）
   三路线对照：甲纯生成 / 乙保真优先 / 丙混合
        ↓
③ 模板合成（Pillow，零消耗）
   人像贴合 / 标题排版 / 标签信息替换
        ↓
④ 自动质检（零消耗）
   人脸相似度 / 人脸裁切 / 文字溢出 / 图层缺失 / 规格达标
        ↓
⑤ 批量导出（零消耗）
   多规格 + 命名规则 + 质检报告
        ↓
   图层化输出（依 P1 选型决定是否走 Figma）
```

### 5.3 阶段 A：小样验证（D02）

**样本量 3-5 张**（因三路对照，从 5-10 张下调），优先覆盖不同缺陷类型：糊 / 光线差 / 背景杂 / 大头与半身混杂。

三路线对照（D03）：

| 路线 | 做法 | 改脸风险 | credits |
|------|------|----------|---------|
| 甲 | 整图直接 image2image | 高 | 1 次/张 |
| 乙 | 程序抠图 → 仅人像 upscale/修复 → 程序合成 | 低 | 1 次/张或零 |
| 丙 | 人脸走乙保真，身体/衣服/边缘走甲美化 | 中低 | 2 次/张 |

**评价机制（替代缺失的人工成品基线）**：

- **客观锚点**：人脸相似度量化 —— 原图人脸与成品人脸特征比对，输出数值。使「改脸」从主观感受变为可设阈值、可自动拦截的指标。此指标在阶段 B 直接复用为质检核心规则。纯本地算法，零消耗。
- **主观判定**：三路同源结果并排，用户只需做**相对排序**（哪张更像本人 / 哪张更能交付），无需给绝对分数。

**退出条件**：若无法证明「不改脸」可控，立即转向 #2 资源位延展（不依赖图像模型，确定性显著更高）。

### 5.4 阶段 B：工具化

验证通过后建设：批量任务管理、异常图筛选、人工修正入口、一键多规格导出、面向运营/产品的操作界面（复用 P0 已还原的界面骨架）。

### 5.5 前置条件（阻塞）

- **内部模型通道信息**（名称 / 接入方式 / 支持的图像能力 / 配额）。此项决定 P2 性质：
  - 若为通用文生图 → 沿用现设计，仅替换 runtime，credits 问题顺带解决
  - 若为人像修复/抠图/超分专用 → **路线乙升为首选，改脸风险近乎归零**（修复而非重绘，天然保脸）
  - 若为码灵 M0 自身接口 → **无需复刻，直接调用**，只需做批量编排 + 质检 + 导出层，前述决策需全部重估
- 3-5 张真实主播原图（越差越有验证价值）
- 1 张海报模板（Figma 源文件或分层 PSD 最佳；仅 JPG 则需手工反推图层与文字框）
- 待替换的信息字段（主播名 / 标签 / 标题，任意格式）

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| **公开 REST API 无「列出个人草稿」接口** ~~无法复刻自动同步~~ | **R7 已推翻** | scope 文档明确本人 token 可访问本人创建的文件；「慢」即遍历式同步的证据 |
| 全量同步耗时长（文件多时请求数线性增长 + 速率限制） | 首次使用体验差 | 异步任务 + 进度轮询；并提供单文件链接快速导入通道 |
| **REST API 无法写回设计内容** | 编辑无法保存回 Figma | 编辑作用于本地数据结构；导出时另行生成文件 |
| 自建画布渲染保真度 | 复杂效果（蒙版、混合模式、矢量布尔、字体缺失）难以还原 | 优先支持 FRAME/RECT/TEXT/IMAGE；复杂节点降级为 REST 渲染的位图 |
| 人脸保真不可控 | P2 业务上作废 | 三路对照 + 相似度阈值拦截；失败即转 #2 |
| credits 仅 80，不足批量（单次活动 400 张） | 无法真跑一次活动 | AI 仅碰人像压低单位消耗；乙路线尽量本地实现；等内部通道确认 |
| 缺人工成品基线 | 质量争论无锚点 | 相似度量化 + 三路相对排序 |
| 吉祥物等私有素材无法复刻 | 视觉不完全一致 | 占位资产 + 预留替换点 |

## 7. 与原产品的能力差距声明

复刻可达成与不可达成的边界，需在动工前明确：

| 能力 | 可复刻 | 说明 |
|------|--------|------|
| 首页与编辑器界面视觉 | ✅ 完全 | 除私有美术素材 |
| 图层树读取与展示 | ✅ 可 | `GET /v1/files/:key` |
| 自建画布渲染与选中交互 | ✅ 可 | 常见节点类型 |
| 本地编辑与导出位图 | ✅ 可 | — |
| 按链接导入 Figma 文件 | ✅ 可 | 需 token |
| **打开即自动同步个人文件** | ✅ **可**（R7 修正） | OAuth + 遍历式同步，慢是固有代价 |
| **编辑后写回 Figma 原文件** | ❌ 不可 | REST 无设计内容写接口 |
